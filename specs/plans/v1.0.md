## Phase 2 — Full regression & final audits ✅ done (2026-08-06)

- [x] `pnpm test:all` green: 266/266 unit tests (56 files), 20 docs e2e, 2 npm-consumer
      e2e, 1 CLI-consumer e2e. (266, not 268 — two dedicated deprecation-alias tests

- [x] Delegated to `a11y-reviewer` and `ssr-safety-reviewer` subagents for a pre-1.0

  - **SSR crash (ssr-safety-reviewer, confirmed empirically against the SSR dev
    server):** `VoltResizableHandle.ngAfterViewInit()` called `syncMeasurements()`
    unconditionally, which calls `getBoundingClientRect()` — that runs during SSR too
    (`ngAfterViewInit` is not browser-only), crashing every server render of
    `/docs/components/resizable` and guaranteeing a hydration mismatch. Fixed by
    wrapping the initial measurement in `afterNextRender()` (matches the existing
    `code-panel.ts` pattern). Re-verified against both the SSR dev server (error gone,
    HTTP 200) and a full production build + `wrangler pages dev` Lighthouse pass
    (CLS 0.00 — confirms no hydration-mismatch layout shift from the fix).
  - **Missing ARIA-contract test coverage (a11y-reviewer):** dialog/drawer unit specs
    never actually opened the overlay, so nothing asserted `role="dialog"`/
    `aria-modal`/`aria-labelledby`; the toast error variant's `role="alert"` had zero
    coverage anywhere. Attempted unit-level tests first, but both are structurally
    untestable in this jsdom + testing-library-angular setup: dialog/drawer's
    `NgpDialog` uses Angular CDK's `Overlay`/`DomPortalOutlet`, which throws
    (`Cannot read properties of undefined (reading 'createEmbeddedView')`) when opened
    via click in jsdom (unlike popover/dropdown-menu/tooltip, which use
    ng-primitives' own lightweight portal and open fine in unit tests); `VoltToast`
    can't render standalone either since `NgpToast` injects an `NgpToastOptions`
    context only `NgpToastManager` ever constructs. Added the assertions to
    `e2e/consumer.spec.ts` instead (real browser, real CDK overlay) — added a second
    error-variant toast trigger to `e2e/consumer/src/main.ts` since none existed.
  - **Informational, not fixed (out of this plan's scope):** `ssr-safety-reviewer` also
    found `window is not defined` inside `ng-primitives@0.110.2` itself (not this
    repo's code) when a listbox has an initial active/selected option during SSR
    (`ng-primitives-internal.mjs` → `getScrollableAncestor`). Needs an upstream
    ng-primitives fix or version bump — flagging for awareness, not fixing here (a
    dependency bump this late in the release needs its own verification pass, out of
    scope for this plan). Also a lower-severity note: `dropdown-menu-trigger.ts`'s
    keyboard-open-first-item logic queries `[role="menuitem"]` against the whole
    `ownerDocument` rather than scoping to its own menu content, so it could pick up
    another open dropdown's items if a consumer renders two at once — not fixed, minor.

## Phase 7 — Third user QA pass: stability for real ✅ done (2026-08-06)

The user reported the vertical resizer misbehaving and the Create Theme CSS block
rendering in the opposite theme, and asked for the remaining `beta` components to be
made genuinely stable — "not just changing the label, check what they're missing and fix
it". Doing that surfaced several components that did not work at all.

- [x] **`resizable` vertical was broken**: the handle owns an `orientation` input that had
      to be hand-synced with its group, and the documented example omitted it, so the
      vertical demo rendered a column-resize bar tracking `clientX` and writing `width`.
      The group's orientation now wins; the input stays as the fallback outside a group.
      The existing unit test had _pinned the bug in place_ — it pressed ArrowRight in a
      vertical group and asserted a resize. Rewrote it to assert the real contract
      (left/right resize a row group, up/down a column group, cross-axis keys inert) and
      added vertical pointer coverage. Verified both axes by dragging in a real browser.
- [x] **`input-otp` was visually dead**: `NgpInputOtpInput` was never in the component's
      `imports`, so `ngpInputOtpInput` was an inert attribute — the hidden input accepted
      text while every slot stayed empty. Also fixed its documented `placeholder`/
      `inputMode` defaults never reaching the primitive and a duplicated `valueChange`
      emission. 11 tests now cover per-slot fill/active/caret movement, paste, pattern
      rejection and the forms contract.
- [x] **`[formControl]` was disconnected on `date-picker`, `input-otp` and `listbox`** —
      all wrote `writeValue()` into their own model rather than the host directive's
      state. Audited every CVA component the same way (does the DOM reflect what the form
      wrote, not just `FormControl.value`); the other 11 were already correct. `listbox`
      had been promoted to `stable` in Phase 6 on the strength of a spec that only tested
      view→form — the missing direction is now a permanent test.
- [x] `navigation-menu`: submenu open, swapping between triggers, Escape and
      `aria-expanded` now covered (was static markup assertions only).
- [x] `file-upload`: `e2e/file-upload.spec.ts` drives a real `DragEvent` chain with a
      populated `DataTransfer`, plus the file-chooser path. Each interaction retries via
      `toPass` because the dropzone is visible in SSR markup before hydration.
- [x] Create Theme's generated CSS used deliberately inverted colors
      (`bg-foreground`/`text-background`) and hand-rolled its own `<pre>`. Extracted the
      editor lifecycle into `src/app/components/code-editor.ts` (removing the third copy
      of that logic) and switched the page to it with `language="css"`.
- [x] **All components are now `stable`.** Verified the public API is unchanged by
      regenerating the API surface and diffing against `specs/api-freeze-0.9.md` — the
      only differences are the three deprecated aliases removed in Phase 1. Every fix was
      internal wiring.
- [x] 285/285 unit tests (was 266), 24 docs e2e, 2 npm-consumer e2e, 1 CLI-consumer e2e,

## Phase 8 — Theme Studio: palette generation + Palette Crafter interop ✅ done (2026-08-06)

- [x] Button demo: Variants was framed and centered while Sizes and States were bare and
      left-aligned. All three sections now share one treatment.
- [x] **Preview panel sticky, for real.** It already carried `lg:sticky lg:top-20`, but
      `overflow-hidden` on the page's `<main>` makes that element a scroll container,
      which disables `position: sticky` for every descendant. `overflow-x-clip` contains
      the decorative blurs without creating the container. Also capped the panel height so
      it scrolls internally instead of outgrowing short viewports. Pinned by an e2e test.
- [x] **`src/app/lib/palette.ts`** — seeded OKLCH palette generation (sRGB ⇄ OKLab ⇄ OKLCH,
      gamut-safe chroma reduction, WCAG contrast) producing all 21 tokens for both modes.
      Accents that land on the lightness crossover where neither white nor near-black text
      reaches AA are walked off it; a 40-seed sweep in the spec asserts every text/surface
      pair clears 4.5:1, which is how that weakness was found in the first place.
- [x] **Palette Crafter interop.** Inspected the live tool to establish the contract
      rather than guessing: its JSON export carries `theme.bg`, `theme.fg`,
      `theme.primary`/`secondary` as 50–950 scales with `DEFAULT`/`foreground`,
      `theme.status` (info/success/warning/danger), and a `meta` block with
      seed/harmony/baseHue/mode. It reproduces palettes from
      `?seed=&mode=&harmony=&baseHue=&algorithm=v2`.
      `paletteFromCrafterExport` maps that onto Volt's tokens (the 50–950 scales are what
      make the opposite mode derivable from a single-mode export), and generated palettes
      link back with their seed/harmony/hue so a palette can be refined there and
      re-imported. No API call is involved — the tool computes client-side, so import is a
      paste and the link is a deep link.
- [x] Fixed duplicate DOM ids on three controls (a static `id` on a Volt component stays
      on the host _and_ is forwarded to the inner control, so `<label for>` resolved to the
      custom element). Found while writing the import test.
- [x] 299/299 unit tests (was 285), 28 docs e2e (was 24), lint, typecheck,
      `check:ai-docs` green.

### Note for a future minor

`VoltTextarea` has no `ariaLabel` input while `VoltInput` does — an `ariaLabel` attribute
on it is silently inert. Not added here: the 1.x public API is frozen, so a new input
belongs in a minor, not this release. The Theme Studio uses a real `<label for>` instead.

### Known, not fixed

- The layout demo templates (`admin-dashboard`, `analytics`, `settings`, `profile`,
  `top-nav`) are desktop app shells rendered in a fixed-height frame; below ~640px they
  compress rather than reflow. Nothing overflows the page and no content is unreachable,
  but making them genuinely responsive is a redesign of the templates themselves, not
  release polish — belongs in its own minor.
- `ng-primitives` 0.110.2 logs `Deprecation warning: Use setLabel() instead of setting
the value directly.` on any page with `volt-progress`. The call is inside
  `ng-primitives-progress.mjs` itself (its `NgpProgressLabel` calls its own deprecated
  setter), so there is nothing to fix on our side — worth an upstream issue.
