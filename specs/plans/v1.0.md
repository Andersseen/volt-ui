## Phase 2 — Full regression & final audits ✅ done (2026-08-06)

- [x] `pnpm test:all` green: 266/266 unit tests (56 files), 20 docs e2e, 2 npm-consumer
      e2e, 1 CLI-consumer e2e. (266, not 268 — two dedicated deprecation-alias tests
      were removed in Phase 1, not a regression.)
- [x] Consumer fixtures (`test:e2e:consumer`, `test:e2e:consumer-cli`) green against the
      final build.
- [x] Delegated to `a11y-reviewer` and `ssr-safety-reviewer` subagents for a pre-1.0
      sweep. Found and fixed real bugs (see below) — same pattern as the v0.9 Phase 1
      sweep that found the `VoltDropdownMenuItem`/`VoltInputOtp` bugs.
  - **SSR crash (ssr-safety-reviewer, confirmed empirically against the SSR dev
    server):** `VoltResizableHandle.ngAfterViewInit()` called `syncMeasurements()`
    unconditionally, which calls `getBoundingClientRect()` — that runs during SSR too
    (`ngAfterViewInit` is not browser-only), crashing every server render of
    `/docs/components/resizable` and guaranteeing a hydration mismatch. Fixed by
    wrapping the initial measurement in `afterNextRender()` (matches the existing
    `code-panel.ts` pattern). Re-verified against both the SSR dev server (error gone,
    HTTP 200) and a full production build + `wrangler pages dev` Lighthouse pass
    (CLS 0.00 — confirms no hydration-mismatch layout shift from the fix).
  - **Missing ARIA-contract test coverage (a11y-reviewer):** dialog/drawer unit specs
    never actually opened the overlay, so nothing asserted `role="dialog"`/
    `aria-modal`/`aria-labelledby`; the toast error variant's `role="alert"` had zero
    coverage anywhere. Attempted unit-level tests first, but both are structurally
    untestable in this jsdom + testing-library-angular setup: dialog/drawer's
    `NgpDialog` uses Angular CDK's `Overlay`/`DomPortalOutlet`, which throws
    (`Cannot read properties of undefined (reading 'createEmbeddedView')`) when opened
    via click in jsdom (unlike popover/dropdown-menu/tooltip, which use
    ng-primitives' own lightweight portal and open fine in unit tests); `VoltToast`
    can't render standalone either since `NgpToast` injects an `NgpToastOptions`
    context only `NgpToastManager` ever constructs. Added the assertions to
    `e2e/consumer.spec.ts` instead (real browser, real CDK overlay) — added a second
    error-variant toast trigger to `e2e/consumer/src/main.ts` since none existed.
  - **Informational, not fixed (out of this plan's scope):** `ssr-safety-reviewer` also
    found `window is not defined` inside `ng-primitives@0.110.2` itself (not this
    repo's code) when a listbox has an initial active/selected option during SSR
    (`ng-primitives-internal.mjs` → `getScrollableAncestor`). Needs an upstream
    ng-primitives fix or version bump — flagging for awareness, not fixing here (a
    dependency bump this late in the release needs its own verification pass, out of
    scope for this plan). Also a lower-severity note: `dropdown-menu-trigger.ts`'s
    keyboard-open-first-item logic queries `[role="menuitem"]` against the whole
    `ownerDocument` rather than scoping to its own menu content, so it could pick up
    another open dropdown's items if a consumer renders two at once — not fixed, minor.
- [x] Accessibility smoke pass in a real browser (`pnpm dev` + `playwright` MCP,
      per `CLAUDE.md`'s protocol): dialog — opens on click, focus moves inside
      automatically (to the first field), `role="dialog"`, Escape closes, focus returns
      to the trigger button — all confirmed via accessibility snapshot, not just
      assertions. Verified the `v1.0.0` header badge and accurate stable/beta labels
      (no experimental) render correctly across dialog/toast/dropdown-menu demo pages.
      Verified dark→light theme toggle re-renders the whole page cleanly (visual
      screenshot). Toast and dropdown-menu spot-checked via snapshot; full keyboard
      contract for every overlay/form component covered by the existing + newly-added
      e2e suite rather than manually walking all ~40 components by hand.
- [x] Bundle/perf re-measurement, repeating the v0.9 Phase 2 method:
  - Library FESM (`dist/volt/fesm2022/voltui-components.mjs`): **422.5 KB raw**
    (v0.9 baseline: 412 KB) — net-neutral, as expected (Phase 1 removed more code —
    two outputs + a manual RxJS bridge constructor — than the SSR fix added).
  - Docs app, **production build** (`pnpm build` + `wrangler pages dev
dist/analog/public`, matching the v0.9 method exactly — an initial trace against
    the unoptimized dev server showed CLS 1.00, which was purely a dev-server/no-
    prerender artifact and not real; discarded in favor of the production measurement):
    home **LCP 102 ms / CLS 0.00**, components grid **LCP 106 ms / CLS 0.00**, resizable
    demo (the component actually touched this phase) **LCP 143 ms / CLS 0.00** — all
    within or better than the v0.9 baseline (113–143 ms LCP, 0.00 CLS on all pages), no
    regression, and CLS 0.00 on the resizable page specifically confirms the
    `afterNextRender` SSR fix causes no hydration-mismatch layout shift.
- [x] Swept "pre-v1"/"before v1"/"release candidate" language and stale 0.9.0/268-test
      stats across `README.md`, `COMPONENT_STATUS.md`, `CONTRIBUTING.md`, `SECURITY.md`,
      `CLI.md`, `introduction.page.ts`, `index.page.ts` (components grid),
      `ai-{prompt,skill,mcp}.page.ts`, `header.ts`, homepage stat tiles. Found and fixed
      real content drift along the way, not just wording: the introduction page's
      Component Catalog listed 9 components (autofill, combobox, date-picker,
      file-upload, listbox, navigation-menu, resizable, sidebar, theme) as
      "experimental", but `COMPONENT_STATUS.md` has had zero experimental components
      for a while — all nine are actually beta. Collapsed the three-column stable/beta/
      experimental layout to two columns on both pages the discrepancy appeared; kept
      the `experimental` label's code plumbing (badge component, `stabilityLabel`/
      `stabilityClass`) as a still-valid future value, just unused today. `SDD.md` and
      `specs/SPEC.md` intentionally left for Phase 3 (they're that phase's own task, not
      stray language to sweep here).
